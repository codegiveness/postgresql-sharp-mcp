## 0.7.0

**Upgrade note (security-relevant behavior changes): two 0.6.0 defaults are loosened so that a plain connection string works.** An omitted `SSL Mode` now means `Prefer` (TLS when the server offers it, certificate never verified, plaintext otherwise) instead of `VerifyFull`, and the database lock's PostgreSQL grant check is now advisory instead of refusing startup. An attacker on the network path can read or impersonate an unverified connection, and in advisory mode PostgreSQL does not confine the login to `POSTGRES_DATABASES`, so SQL can still reach other databases where the login's privileges allow. **To restore the 0.6.0 behavior,** put `SSL Mode=VerifyFull` in the connection string (plus `Root Certificate=<CA file>` for a private CA) and set `POSTGRES_DATABASE_LOCK_MODE=strict`. Run `--validate` before reconnecting; see the [README upgrade note](README.md#upgrading-an-existing-installation).

- **Breaking (security-relevant):** TLS verification is no longer the default. A connection string (base `POSTGRES_CONNECTION_STRING`/`--connection-string` or any targets JSON/file profile) that does not set `SSL Mode` now gets `SSL Mode=Prefer` for every host, loopback included. 0.6.0 used `VerifyFull` for non-loopback hosts and `Disable` for loopback and Unix sockets. An explicit `SSL Mode` is used unchanged. **Restore the 0.6.0 behavior** with `SSL Mode=VerifyFull` in the connection string, plus `Root Certificate=<CA file>` for a private CA. There is deliberately no `POSTGRES_TLS_MODE` setting: the connection string's `SSL Mode` is the single place TLS is configured, and targets profiles can differ. A PostgreSQL without TLS, such as one reached as `host.docker.internal`, now works by default.
- A connection string with `Root Certificate=` but no `SSL Mode` still gets `SSL Mode=VerifyFull` (Npgsql's `Prefer` would ignore the CA file), so 0.6.0 profiles that followed the `tls_verification_failed` advice keep verification without changes.
- Clearer configuration errors that never show the rejected value: a `postgres://`/`postgresql://` URL in `POSTGRES_CONNECTION_STRING`/`--connection-string` or a targets profile, an invalid Npgsql connection string, a `POSTGRES_DATABASES` value that is not a JSON array, and an unreadable targets file each name the setting and the expected form instead of the generic "Invalid targets configuration".
- `tls_verification_failed` and `tls_unavailable` now occur only with an explicit `VerifyCA`/`VerifyFull` (and `tls_unavailable` also with `Require`).
- TLS warning reworded as advice. A non-blocking `[warning]` is printed for every profile whose host is not loopback or a Unix-domain socket and whose mode is not `VerifyCA`/`VerifyFull`, including the `Prefer` default. For `Prefer` it says the connection encrypts only if the server offers TLS and never verifies the certificate, that this is fine on a trusted network, and how to harden it with `SSL Mode=VerifyFull` (and `Root Certificate=<CA file>` for a private CA). The wording is adapted for `Disable`, `Require` and `Allow`.
- **Breaking (security-relevant):** the database lock's PostgreSQL grant check is advisory by default. `POSTGRES_DATABASES`/`--databases` is still enforced by the server on every path in both modes (`invalid_target` before connecting, `list_databases` listing only the locked names, no fallback, and no session is ever opened on an out-of-lock database). The grant check still runs at startup and in `--validate`, but each finding prints as `[warning] database lock (advisory): <finding>` (at most 32, then `... N more findings.`) followed by one summary line, startup continues, and `--validate` exits 0 when connections succeed. **Restore the 0.6.0 behavior** with `POSTGRES_DATABASE_LOCK_MODE=strict` (or `--database-lock-mode strict`) after hardening the role ([SECURITY.md](SECURITY.md#database-lock-hardening)).
- New setting `POSTGRES_DATABASE_LOCK_MODE` / `--database-lock-mode`: `advisory` (default) or `strict`. The CLI value overrides the environment. Any other value is a startup error (`POSTGRES_DATABASE_LOCK_MODE/--database-lock-mode must be advisory or strict.`), and `strict` without a configured lock is a startup error (`POSTGRES_DATABASE_LOCK_MODE/--database-lock-mode is strict, but no POSTGRES_DATABASES/--databases database lock is configured.`). In strict mode a failed check prints `[startup] Refusing to start: the PostgreSQL check for the configured database lock (POSTGRES_DATABASES) failed and POSTGRES_DATABASE_LOCK_MODE is strict.` plus the findings and exits 1 (`--validate` exits 1), exactly as 0.6.0 did. A clean check in either mode prints `[startup] Database lock verified: PostgreSQL grants confine every configured login to POSTGRES_DATABASES.` `POSTGRES_REQUIRE_DATABASE_LOCK`/`--require-database-lock` is unchanged and only requires that a lock is configured.
- An advisory-mode lock check that cannot connect is only a warning. 0.6.0 refused startup when a locked profile was unreachable; the server now starts and tool calls report the connection error. Strict mode still refuses.
- `list_databases` adds `"database_lock_mode": "advisory"|"strict"` next to the existing `database_lock` boolean; the field is omitted when there is no lock (`database_lock: false`). Existing fields are unchanged. With a lock, the `initialize` instructions and the `execute_sql`/`list_databases` descriptions state the mode: strict says PostgreSQL grants were verified at startup to confine the login to the listed databases, advisory says the grants were not required to confine the login, so SQL may still reach other databases where the login's privileges allow.
- Documentation: README quick start shows only a plain connection string and a new "Hardening for advanced users" section covers `SSL Mode=VerifyFull`, strict lock mode, a least-privileged role and restricted access mode; SECURITY.md describes both lock modes and what advisory mode does and does not protect against; the architecture, assurance case and security posture documents describe the new defaults. Superuser and privileged-role `[warning]` lines from `--validate`, the default `unrestricted` access mode, limits, pools and the rejection of `postgres://` URLs are unchanged.

## 0.6.0

**Upgrade note (breaking): TLS is now verified by default.** A connection string that does not set `SSL Mode` now uses `SSL Mode=VerifyFull` for a non-loopback host (previously Npgsql's unverified `Prefer`, which could fall back to plaintext) and `SSL Mode=Disable` for loopback and Unix sockets. A remote server with a private CA now fails with `tls_verification_failed` until the profile adds `Root Certificate=<CA file>`, and a remote server without TLS fails with `tls_unavailable`. Profiles that set `SSL Mode` explicitly are unchanged. **Before upgrading**, run `--validate` with 0.6.0 against your configuration. **Rollback:** set `SSL Mode=Prefer` explicitly on an affected profile to restore the previous behavior for it on 0.6.0, or pin 0.5.0 (`dotnet tool update --global codegiveness.postgresql-sharp-mcp --version 0.5.0`, or `@0.5.0` in the npx `args`). Details are in the first entry and in the [README upgrade notes](README.md#upgrading-an-existing-installation). Tool names, parameters, environment variables, CLI flags and the targets-file format are unchanged. Everything else below is a fix, documentation, policy or tooling.

- **Breaking:** verified TLS by default. A connection string (base `POSTGRES_CONNECTION_STRING`/`--connection-string` or any targets JSON/file profile) that does not set `SSL Mode` previously got Npgsql's `Prefer`, which uses TLS without verifying the server and silently falls back to plaintext. It now gets `SSL Mode=VerifyFull` when its host is not loopback (certificate chain and host name are verified before any credential is sent, with no plaintext or unverified fallback) and `SSL Mode=Disable` when every host is `localhost`, `127.0.0.0/8`, `::1` or a Unix-domain socket (no TLS is used, so no TLS without verification; a `Root Certificate` on such a profile selects `VerifyFull`). An explicit `SSL Mode`, including `Prefer`, `Require` and `Disable`, is the operator's opt-out and is honored unchanged; the existing startup/`--validate` `[warning]` still flags non-loopback profiles without `VerifyCA`/`VerifyFull`. New fixed errors, on stderr for `--validate` and as structured tool errors, name only the profile and the fix: `tls_verification_failed` (untrusted CA or host name not in the certificate: add `Root Certificate=<CA file>`, or opt out with `SSL Mode=Require`) and `tls_unavailable` (the server offers no TLS: enable it, or opt out with `SSL Mode=Disable`). **Upgrade guidance:** servers with a publicly trusted certificate need no change; a private CA needs `Root Certificate=<absolute CA file path>`; a non-TLS remote server, including a host PostgreSQL reached as `host.docker.internal`, needs `SSL Mode=Disable`; a loopback or forwarded server that requires TLS (`hostssl` rules) needs an explicit `SSL Mode`. To restore the old behavior for a profile add `SSL Mode=Prefer` explicitly. Run `--validate` before reconnecting your client. `--help`, README, SECURITY and the assurance case are updated. Verifier: a disposable TLS container with a throwaway CA proves that an unset mode refuses an unverifiable non-loopback server before the login is sent (the server log shows no user), succeeds with `Root Certificate`, honors `Require` and `Disable` with the warning, rejects a host name missing from a trusted certificate, and uses plaintext on loopback.
- A connection the server resets during login now reports `connection_error` instead of `internal_error` ("Unexpected server failure"), and the startup database-lock check reports it as a connection finding instead of failing. Npgsql 10.0.3 can let a raw `SocketException` escape while it applies a socket timeout to a connection that was already reset; the package verifier hit this on macOS when opening a loopback profile without TLS.

## 0.5.0

Upgrade notes: a locked configuration whose login can execute server-file functions is now refused at startup, and npm installs that omit optional dependencies now fail (both below). Existing tool names, parameters, environment variables, CLI flags and the targets-file format remain compatible; additions such as the `parameters` input of `execute_sql`/`explain_query` are optional.
- npm: the 177 MB package that bundled all five platform runtimes is split into a main package of about 140 KB and five platform packages of 35–39 MB each (`@codegiveness/postgresql-sharp-mcp-win32-x64`, `-linux-x64`, `-linux-arm64`, `-darwin-x64`, `-darwin-arm64`). The main package lists them as `optionalDependencies`, so npm, npx and global installs download only the package matching the machine's OS, CPU and (on Linux) glibc. The install command, `--allow-scripts` approval, `bin` name and installed native server are unchanged. The upstream `run-script-os` runner and the installation-time `uname` call are no longer used. An install that omits optional dependencies (`--omit=optional`) or runs on an unsupported platform such as Alpine/musl now fails with `postgresql-sharp-mcp-npm-install: not found`, where the old installer printed the supported-platform list; see the README troubleshooting table. Releases stage the platform packages before the main package. Each new package name needs a one-time npm trusted-publisher setup; see CONTRIBUTING.
- Security: the database lock check now also refuses startup when the login, or any role it can `SET ROLE` to (including through `NOINHERIT` or `INHERIT FALSE` memberships), holds `EXECUTE` on a server-file function (`pg_read_file`, `pg_read_binary_file`, `pg_ls_dir`, server-side `lo_import`/`lo_export`, adminpack `pg_file_write`/`pg_file_unlink`/`pg_file_rename`) in any reachable locked database. Such a grant needs no `pg_read_server_files` membership, and `pg_read_binary_file` can read other databases' relation files from the data directory, bypassing the lock. Existing locked configurations with such grants are now refused; revoke the grant as described in the [hardening guide](SECURITY.md#database-lock-hardening).
- Fix: a connection-string database lock (`POSTGRES_DATABASES`) with more than 32 names, or with names × `POSTGRES_POOL_SIZE` above 256, was refused at startup with "Configure 1..32 database targets." Lock names are `target` aliases of one connection-string login profile; the 32-profile and profiles × pool-size limits now count only targets JSON/file profiles (a connection string counts as one). The runtime pool cache bound (`floor(256 / POSTGRES_POOL_SIZE)` data sources) is unchanged.
- Security warnings that never block startup: startup and `--validate` print a `[warning]` on stderr naming every profile that reaches a non-loopback host without certificate verification (`SSL Mode` other than `VerifyCA`/`VerifyFull`, including the Npgsql default `Prefer`); profiles with the same host, port, user and mode, such as a connection-string lock's aliases, share one line. `--validate` also warns when a configured login is or can become a superuser, belongs to `pg_execute_server_program`, `pg_write_server_files`, `pg_read_server_files`, `pg_signal_backend` or `pg_checkpoint`, or reaches a `REPLICATION`/`BYPASSRLS` role. These capabilities act through `SELECT` inside READ ONLY transactions, so restricted mode and read-only annotations do not contain them. Warnings name profiles and roles only, never connection strings, and a failing check only omits its warning.
- Fix: what agents are told now follows the enforced access mode and database lock. In restricted mode the `execute_sql` description no longer advertises `read_only=false` writes and says they are refused; in unrestricted mode it explains the write opt-in. Under a database lock, `list_databases` no longer claims new databases need no configuration edit, and both it and `execute_sql` say only listed databases can be selected. `initialize` now returns server instructions naming the access mode, the database lock and result/time limits; `list_databases` adds `database_lock`. A `25006` read-only rejection now tells unrestricted-mode agents to retry with `read_only=false` if a write is intended (the target must also accept writes, so not a standby), and the restricted-mode refusal names the access mode. The misleading `ReadOnly = true, Destructive = false` declaration on `execute_sql` is removed; annotations were and remain set from the access mode at registration (unrestricted: `readOnlyHint=false`, `destructiveHint=true`).
- Every tool parameter now has a short description listing allowed values or defaults (`section`, `format`, `order_by`, `limit` and its `max_rows` cap, `offset`, `target`, …), so agents no longer discover them from error round trips. The restricted `tools/list` array grows from 6,780 to 10,516 bytes.
- SQL errors are now actionable without exposing data values. Errors for statements submitted to `execute_sql` and `explain_query` include `position`, PostgreSQL's 1-based character position mapped into the submitted statement (previously absent; the server's paging/EXPLAIN wrapper would also have shifted it). SQLSTATE class `42` errors (syntax, undefined/ambiguous objects, privileges) that PostgreSQL positions inside the submitted statement, and `42501` privilege errors, add `server_message` and `server_hint` when not raised inside a routine or internal query; execution-time class `42` errors that can echo row values (`current_setting(col)`, `col::regclass`, `query_to_xml`) stay withheld. Class `23` integrity errors not raised from a routine add `constraint`. All other PostgreSQL messages, hints and details remain withheld, and the fallback summary no longer claims the message is withheld when `server_message` is returned. Existing `code`, `message` and `sql_state` fields are unchanged.
- `execute_sql` and `explain_query` accept optional `parameters`: up to 256 JSON scalars bound to `$1..$n`, never interpolated into the SQL. Each value is sent as PostgreSQL `unknown`, so its type is inferred from context like a quoted literal; cast when ambiguous. Objects and arrays return `invalid_parameters`, and new fixed summaries cover too few values (`08P01`) and an undeterminable parameter type (`42P18`, which also results from extra values or a skipped `$n`). Paging with `next_offset` must resend the same `sql` and `parameters`. Existing calls are unchanged.
- Performance: every tool call saves one network round trip. The transaction setup (`SET TRANSACTION READ ONLY`/`READ WRITE`, `standard_conforming_strings`, statement and lock timeouts) now travels in the same batch as the first statement. With 25 ms added to each server response, median `execute_sql` latency fell from 106.8 ms to 80.8 ms. `SqlSession` no longer exposes its connection, transaction or any batch: it builds and owns every batch itself and prepends any pending setup, so no caller can run SQL before the transaction mode is set.
- Document PostgreSQL 13 as the supported minimum with per-feature notes in the README. `get_top_queries` now adapts to the installed `pg_stat_statements` version: with extension 1.8 (no `toplevel`, as on PostgreSQL 13 or an upgraded cluster) it works and returns `toplevel` as null, explained in `notes`; below 1.8 it returns the specific `extension_outdated` error telling the administrator to run `ALTER EXTENSION pg_stat_statements UPDATE`, replacing the generic "A referenced column does not exist." (42703). On PostgreSQL 14+ with a current extension the result is unchanged. The `extension_missing` and `extension_not_ready` (55000) messages no longer assume `shared_preload_libraries` is editable, so they fit managed services.
- Verifier and CI: `POSTGRES_FIXTURE_MAJOR` (13–18, default 17) selects the integration fixture's PostgreSQL major, which is pulled by manifest-list digest with HypoPG at an exact pgdg version. CI runs the integration scenarios for 13–16 and 18 in a new `integration` matrix job next to the existing PostgreSQL 17 `verify` job. A new scenario installs `pg_stat_statements` 1.8 and 1.7 to cover the adaptation.
- `--help` now lists every option with its environment variable, default, bounds and precedence (environment connection string over `--connection-string`, targets JSON over file, connection string versus targets exclusivity), including `POSTGRES_ACCESS_MODE`, `POSTGRES_QUERY_TIMEOUT` and `POSTGRES_LOG_LEVEL`, matching `ServerOptions.Parse`. The help text is hand-written, not generated from the parser. It states that a connection string creates the `primary` profile only without a database lock, that with `--databases` each locked name is a target alias of that one login profile, that only targets profiles count toward the pool-size budget, and that `--validate` also prints privilege/TLS warnings.
- Range errors for `--query-timeout` now name the option that was used (`--query-timeout must be 1..600.`) instead of `POSTGRES_QUERY_TIMEOUT`; the environment variable still reports its own name. The message wording is the only behavior change; exit code and valid ranges are unchanged.
- README: add a Docker subsection (build from source, MCP client JSON with explicit `-e` forwarding of every setting because the MCP `env` block reaches only the `docker` CLI, `127.0.0.1` inside a container, non-root targets-file permissions), rollback guidance for the 0.4.0 database-lock startup refusal (including removing `--require-database-lock` when pinning 0.3.3, which rejects it), the lock-name and alias rules, and the note that the `postgres` default bootstrap database applies to connection-string mode only.
- Documentation: attribute the discovery and unrestricted-default contract to 0.3.1. Source version 0.3.0 was never tagged or released; README, CONTRIBUTING and the security posture no longer say 0.3.0 or newer is required.
- Verifier only, no runtime change: `integration` now cancels a long `execute_sql` with MCP `notifications/cancelled` and asserts the PostgreSQL backend stops, no response is sent and every pooled connection can run a query concurrently afterwards (two simultaneous queries at `POSTGRES_POOL_SIZE=2`); `sarif-regressions` now requires each rejection case to fail with its specific exception type and message instead of any of four exception types.
